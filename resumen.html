1. Formatos de datos

Hoy es más fácil y barato recopilar y almacenar información. Los datos bien gestionados y analizados generan valor y mejoran la toma de decisiones.

Los datos se organizan en entidades (objetos del mundo real, p. ej. un cliente) que tienen atributos (características, p. ej. nombre o correo).

Clasificación según su estructura

  • Estructurados: esquema fijo; todas las instancias tienen los mismos campos. Tablas con filas y columnas. Ej.: tabla de clientes en una BD relacional.
  • Semiestructurados: tienen estructura, pero puede variar entre instancias (campos opcionales, listas, objetos anidados). Formato jerárquico. Ej.: JSON.
  • No estructurados: sin estructura definida. Ej.: documentos, imágenes, audio, video, binarios.

2. Almacenamiento de archivos

Cada vez se usa más el almacenamiento en la nube. El formato elegido depende de:

  • El tipo de datos (estructurados, semi o no estructurados).
  • Las aplicaciones y servicios que leerán, escribirán y procesarán los datos.
  • Si deben ser legibles por personas o si se necesita optimizar almacenamiento y procesamiento.

Formatos comunes

  • Texto delimitado: datos tabulares separados por un delimitador. Los más comunes: CSV (comas) y TSV (tabulaciones).
  • JSON (JavaScript Object Notation): ligero y legible; esquema jerárquico de objetos con atributos. Ideal para intercambio entre aplicaciones y sistemas distribuidos.
  • XML (Extensible Markup Language): usa etiquetas para elementos y atributos. Popular en los 90 y 2000; hoy desplazado en gran parte por JSON, aún presente en sistemas legacy.
  • BLOB (Binary Large Object): todo archivo se guarda como binario, pero el término se usa para imágenes, audio, video y archivos propios de aplicaciones.

Formatos optimizados

  • Avro: orientado a filas (Apache). Encabezado JSON con el esquema; datos en binario por bloques de registros. Bueno para serializar y transmitir.
  • ORC (Optimized Row Columnar): columnar, creado por Hortonworks para optimizar lecturas y escrituras en Apache Hive.
  • Parquet: columnar (Apache). Agrupa datos por columna: compresión eficiente y lectura solo de las columnas necesarias. Estándar de los lakehouses.
  • Delta Lake: no es un formato nuevo, es una capa de tablas sobre Parquet con un registro de transacciones (log). Permite ACID, control de versiones y actualizaciones confiables sobre un data lake. Creado por Databricks, código abierto.

3. Bases de datos

Una base de datos es un sistema central donde se almacenan y consultan datos.

Relacionales

Principalmente para datos estructurados.

  • Tablas con filas y columnas; cada fila es una instancia de una entidad.
  • Cada fila se identifica con una clave principal (primary key).
  • Las tablas se relacionan mediante claves foráneas (foreign keys): permite normalizar y evitar duplicados.
  • Cada columna tiene un tipo de dato definido (esquema fijo).
  • Se consultan y administran con SQL.

No relacionales (NoSQL = "Not only SQL")

Para datos semiestructurados y no estructurados.

  • No imponen un esquema relacional ni estructura tabular fija.
  • Esquema flexible: dos registros de la misma colección pueden tener campos distintos.
  • Cada registro se identifica con una clave única.
  • Cada motor tiene su propia API o lenguaje de consulta (NoSQL no es un lenguaje).

Cuatro tipos NoSQL

  • Clave-valor: clave única + valor en cualquier formato.
  • Documentos: clave-valor donde el valor es un documento (normalmente JSON) consultable por sus campos.
  • Familias de columnas: filas y columnas, con columnas agrupadas en familias relacionadas.
  • Grafos: entidades como nodos y relaciones como aristas. Ideales cuando importan las relaciones (redes sociales).

4. Procesamiento transaccional (OLTP)

Un sistema transaccional registra transacciones: eventos concretos que la organización quiere rastrear (ventas, pagos, inventario...). Se conoce como OLTP (Online Transaction Processing).

  • Bases optimizadas para lecturas y escrituras rápidas de registros individuales (CRUD: crear, leer, actualizar, eliminar).
  • Integridad y consistencia mediante las propiedades ACID (ver glosario).
  • Cargas operativas: muchas transacciones pequeñas, concurrentes y de alta disponibilidad.

5. Procesamiento analítico

Trabaja con grandes volúmenes de datos históricos para obtener métricas e información de negocio. Sistemas de solo lectura (o lectura mayoritaria).

Arquitectura típica

  1. Ingesta: datos operativos (OLTP) a un data lake mediante:
    • ETL: extraer → transformar → cargar.
    • ELT: extraer → cargar → transformar (habitual en lakehouses).
  2. Modelado en tablas: en un lakehouse (tablas sobre archivos del lago) o en un data warehouse (motor SQL relacional).
  3. Agregación: modelo OLAP, hoy modelo semántico (antes "cubo"). Las medidas de las tablas de hechos se calculan por dimensiones. Ej.: ventas por fecha, cliente y producto. Ejemplo más común: modelos semánticos de Power BI.
  4. Consumo: informes, visualizaciones y paneles.

Componentes

  • Data lake: grandes volúmenes de archivos en su formato original.
  • Data warehouse: esquema relacional optimizado para lecturas. Puede requerir desnormalizar datos del origen OLTP (duplicados a propósito para consultas más rápidas).
  • Data lakehouse: almacenamiento flexible del lake + consultas relacionales del warehouse.
  • Modelo OLAP / semántico: datos preagregados por dimensiones y niveles jerárquicos (región → ciudad → dirección); consultas de resumen muy rápidas.

Quién usa cada capa

  • Científicos de datos: archivos del data lake, para explorar y crear modelos.
  • Analistas de datos: tablas del data warehouse, para informes y visualizaciones complejas.
  • Usuarios de negocio: datos preagregados del modelo semántico en informes y paneles.

Plataformas de análisis en Azure

  • Microsoft Fabric: SaaS unificada: almacenamiento, ingeniería, data warehouse e informes en un área de trabajo.
  • Azure Databricks: ingeniería y ciencia de datos a gran escala; usa Delta Lake.
  • Microsoft Purview: gobernanza, seguridad y cumplimiento de datos en todos los orígenes.
  • Fabric y Databricks incluyen Copilot para explorar datos en lenguaje natural.

Arquitectura medallón (lakehouse)

  • Bronze: datos crudos, tal como llegan del origen.
  • Silver: datos limpios y estandarizados (sin duplicados, tipos homogéneos).
  • Gold: datos agregados y listos para el negocio, modelados para informes.

Ventaja: cada capa tiene un nivel de calidad claro y siempre se puede reprocesar desde Bronze si cambian los requisitos.

1. Roles de trabajo

Hay roles orientados al negocio, a la ingeniería, a la investigación e híbridos. Cada organización puede nombrarlos distinto y una persona puede desempeñar varios.

Ej.: como DBA aprovisiona una BD transaccional y, como ingeniero de datos, crea la canalización que copia esos datos a un data warehouse.

DBA Administrador de bases de datos

  • Diseña, implementa, mantiene y opera BD locales y en la nube.
  • Disponibilidad, rendimiento y optimización.
  • Copias de seguridad y recuperación ante desastres.
  • Seguridad: concede o deniega permisos.
  • IA: diagnosticar rendimiento y escribir consultas en lenguaje natural.

ING Ingeniero de datos

  • Canalizaciones de ingesta, limpieza y transformación; almacenes para análisis.
  • Trabaja con BD relacionales y no relacionales, archivos y streaming.
  • Privacidad de los datos desde el entorno local hasta la nube.
  • Administra y supervisa las canalizaciones.
  • IA: generar código de transformación y sugerir configuraciones.

ANA Analista de datos

  • Maximiza el valor de los datos de la empresa.
  • Explora tendencias y relaciones, diseña modelos analíticos, crea informes y visualizaciones.
  • Convierte datos crudos en información útil según el negocio.
  • IA: resumir informes, sugerir visualizaciones, generar medidas DAX.

IA Ingeniero de IA

  • Crea e integra funciones con IA en apps y flujos de datos.
  • Trabaja con LLM, canalizaciones de ML y orígenes de datos.
  • Escenarios: chat sobre los datos, generación de contenido, clasificación automática.
  • Colabora con ingenieros (preparan datos) y analistas (muestran resultados de IA).
  • Plataforma principal: Microsoft Foundry.
  • Diseño, evaluación e IA responsable siguen siendo tareas humanas.
Otros roles (no cubiertos): científico de datos, arquitecto de datos, desarrollador de aplicaciones, ingeniero de software.
Idea clave: todos los roles usan IA como asistente, pero el criterio del profesional sigue siendo necesario.

2. Servicios de datos en Azure

No hace falta memorizarlos todos: lo importante es saber qué tipo de herramienta es cada uno y qué rol la usa.

Modelos de entrega en la nube

  • IaaS: Microsoft da la VM; tú administras SO y software.
  • PaaS: Microsoft administra infraestructura (servidores, parches, respaldos); tú te centras en datos y app.
  • SaaS: producto completo listo para usar por internet.

Azure SQL DBAINGANA

Familia de BD relacionales basadas en SQL Server. De menos a más control (y administración):

  • Azure SQL Database: PaaS totalmente administrada.
  • SQL Managed Instance: instancia de SQL Server con mantenimiento automatizado; más configurable, más responsabilidad.
  • SQL Server en VM (IaaS): control y administración totales.

DBA: BD de apps de línea de negocio (LOB). Ingeniero: origen de ETL. Analista: consulta directa (en empresas grandes se combina antes en un almacén analítico).

BD de código abierto DBAINGANA

  • Azure Database for MySQL: fácil de usar; pila LAMP (Linux, Apache, MySQL, PHP).
  • Azure Database for PostgreSQL: objeto-relacional; admite tipos de datos personalizados no relacionales.

Azure Cosmos DB DEVDBAING

  • BD NoSQL de escala global con varias API: documentos JSON, clave-valor, familias de columnas y grafos (los 4 tipos del módulo 1).
  • Normalmente la administran los desarrolladores como parte de la app.
  • Ingenieros la integran en soluciones analíticas.

Azure Storage ING

  • Contenedores de blobs: archivos binarios, escalable y barato.
  • Recursos compartidos de archivos: carpetas de red.
  • Tablas: clave-valor para lecturas y escrituras rápidas.

Data lake = blob storage + espacio de nombres jerárquico (carpetas en un sistema de archivos distribuido).

Azure Data Factory ING

  • Define y programa canalizaciones para mover y transformar datos (ETL).
  • Llena almacenes analíticos con datos transaccionales.
  • Fabric Data Factory: versión dentro de Fabric; recomendada si todo vive en Fabric.

Datos relacionales, normalización y SQL

learn.microsoft.com/training/modules/explore-relational-data-offerings

1. Datos relacionales

  • Las entidades del mundo real (objetos y eventos importantes) se modelan como tablas. Ej. tienda: clientes, productos, pedidos y líneas de pedido.
  • Cada fila es una sola instancia de la entidad (un cliente, un producto, un pedido).
  • Son datos estructurados: todas las filas tienen las mismas columnas.
  • Una columna puede quedar vacía: valor NULL. Ej.: MiddleName de un cliente sin segundo nombre.

Tipos de datos

Cada columna guarda un tipo de dato específico:

  • Texto (longitud fija o variable): Email
  • Decimal: Price
  • Entero: Quantity
  • Fecha y hora: OrderDate

Los tipos disponibles dependen del sistema, pero la mayoría admite los tipos estándar de ANSI.

2. Normalización

Proceso de diseño del esquema que minimiza la duplicación y asegura la integridad de los datos. Definición práctica:

  1. Cada entidad en su propia tabla.
  2. Cada atributo discreto en su propia columna.
  3. Cada fila identificada con una clave principal (PK).

4. Objetos de base de datos

Además de tablas, una BD relacional tiene estructuras que organizan los datos, encapsulan acciones y aceleran el acceso.

Vista

Tabla virtual basada en el resultado de un SELECT: una "ventana" a filas de una o varias tablas.

CREATE VIEW Deliveries
AS
SELECT o.OrderNo, o.OrderDate,
       c.FirstName, c.LastName,
       c.Address, c.City
FROM Order AS o JOIN Customer AS c
ON o.Customer = c.ID;

Se consulta y filtra igual que una tabla:

SELECT OrderNo, OrderDate, LastName, Address
FROM Deliveries
WHERE City = 'Seattle';

Procedimiento almacenado

Instrucciones SQL guardadas que se ejecutan a petición. Encapsulan la lógica que las aplicaciones necesitan; pueden recibir parámetros.

CREATE PROCEDURE RenameProduct
    @ProductID INT,
    @NewName   VARCHAR(20)
AS
UPDATE Product
SET Name = @NewName
WHERE ID = @ProductID;

Se ejecuta con EXEC:

EXEC RenameProduct 201, 'Spanner';

Índice

Ayuda a buscar datos más rápido, como el índice al final de un libro: entradas ordenadas que apuntan a la página correcta, sin leer todo el libro.

  • Se crea sobre una columna: guarda una copia ordenada de esos valores con punteros a las filas.
  • Si una consulta filtra por esa columna en el WHERE, el sistema usa el índice en vez de recorrer la tabla fila por fila.
  • Internamente es una estructura de árbol que usa el optimizador de consultas.
CREATE INDEX idx_ProductName
ON Product(Name);

Cuándo sí y cuándo no:

  • En tablas con pocas filas no aporta: el optimizador lo ignora y lee la tabla completa.
  • En tablas con muchas filas mejora mucho las consultas.
  • Una tabla puede tener varios índices (p. ej. otro sobre Price).
Costo: ocupan almacenamiento y hay que mantenerlos en cada INSERT, UPDATE y DELETE, lo que vuelve más lentas esas operaciones. Hay que equilibrar la velocidad de las consultas con el costo de las escrituras.

1. Azure Blob Storage

Almacena grandes cantidades de datos no estructurados como blobs (objetos binarios grandes) en la nube. Las apps los leen y escriben con la API de Blob Storage.

Organización

  • Los blobs viven en contenedores dentro de una cuenta de Azure Storage.
  • Un contenedor agrupa blobs relacionados; el acceso de lectura y escritura se controla a nivel de contenedor.
  • Inicio de sesión recomendado: Microsoft Entra ID con RBAC (control de acceso basado en roles) para dar permisos precisos.
  • Carpetas virtuales: por defecto son solo un / en el nombre del blob. No permiten controlar acceso ni hacer operaciones masivas por carpeta.

Ej.: ventas/2026/enero.csv es un solo blob cuyo nombre contiene "/".

Tres tipos de blob

Blob en bloques

  • Conjunto de bloques de hasta 4000 MiB cada uno; máximo 190,7 TiB (50 000 bloques).
  • El bloque es la unidad mínima de lectura y escritura.
  • Para objetos grandes y discretos que cambian poco (imágenes, videos, documentos).

Blob en páginas

  • Páginas fijas de 512 bytes; hasta 8 TB.
  • Optimizado para lecturas y escrituras aleatorias de páginas sueltas.
  • Azure lo usa para los discos virtuales de las VM.

Blob en anexos

  • Blob en bloques optimizado para agregar al final; no se pueden modificar ni borrar bloques existentes.
  • Bloques de hasta 4 MB; máximo ~195 GB.
  • Ideal para registros (logs).

2. Azure Data Lake Storage Gen2

Lago de datos a escala de nube integrado en Azure Storage. Combina la escalabilidad y el control de costos de Blob Storage (niveles y ciclo de vida) con un sistema de archivos jerárquico compatible con los sistemas de análisis.

  • Azure Databricks puede montarlo como sistema de archivos distribuido para procesar grandes volúmenes.
  • OneLake de Microsoft Fabric está construido sobre él.
  • El espacio de nombres jerárquico habilita ACL compatibles con POSIX: permisos de lectura, escritura y ejecución por archivo y carpeta, aparte de RBAC.
  • Se activa con la opción Espacio de nombres jerárquico de la cuenta de Storage, al crearla o después.
La actualización es de un solo sentido: una vez habilitado el espacio de nombres jerárquico, no se puede volver a un espacio de nombres plano.

3. Microsoft OneLake

Un solo lago de datos lógico para toda la organización. Viene automáticamente con cada inquilino (tenant) de Microsoft Fabric y es el repositorio central de los datos de análisis.

  • Admite cualquier tipo de archivo, estructurado o no.
  • Varios motores analíticos usan los mismos datos sin moverlos ni duplicarlos.

Ventajas clave

  • Un lago para toda la organización, en vez de un lago por área.
  • Propiedad distribuida: cada área administra sus datos en sus áreas de trabajo, con límites de gobernanza.
  • Abierto y compatible: guarda en formato Delta Parquet y admite las API y SDK de ADLS Gen2.
  • Fácil de navegar desde Windows con el explorador de archivos de OneLake.

Idea: "OneLake es el OneDrive de los datos".

4. Azure Files

Crea recursos compartidos de archivos de red en la nube, como los de una red corporativa. Los recursos compartidos locales no escalan bien con muchos usuarios o con sedes distintas; en Azure se eliminan costos de hardware y mantenimiento y se gana alta disponibilidad.

Capacidad y límites

  • Se crea dentro de una cuenta de almacenamiento.
  • Hasta 256 TiB por cuenta SSD (más en HDD), repartidos en cualquier número de recursos compartidos.
  • Archivo individual de hasta 4 TiB; se pueden fijar cuotas por recurso compartido.

5. Azure Table Storage

Almacenamiento NoSQL clave-valor en tablas. Cada elemento es una fila con columnas para sus campos.

No es como una tabla relacional: guarda datos semiestructurados; las columnas pueden variar por fila y no hay claves foráneas, relaciones, procedimientos almacenados ni vistas.
  • Cada fila tiene una clave única: PartitionKey + RowKey.
  • Una columna Timestamp registra la fecha de la última modificación.
  • Datos desnormalizados: cada fila contiene toda la entidad (un cliente con todos sus teléfonos y direcciones). En una BD relacional irían en varias tablas.

Particiones

Agrupan filas relacionadas que comparten la PartitionKey y se guardan juntas.

  • Son independientes y crecen o se reducen solas; una tabla admite cualquier número.
  • Incluir la PartitionKey en la búsqueda reduce la E/S y mejora el rendimiento.
  • Dentro de una partición, las filas se guardan ordenadas por RowKey.

Tipos de consulta rápidas

  • Consulta de punto: una sola fila (PartitionKey + RowKey).
  • Consulta por rango: un bloque contiguo de filas en una partición.

1. ¿Qué es Azure Cosmos DB?

  • Base de datos NoSQL totalmente administrada PaaS: Microsoft se encarga de servidores, parches, actualizaciones y respaldos.

  • Se agregan regiones a la cuenta en cualquier momento y los datos se replican solos.

La capacidad se mide en unidades de solicitud por segundo (RU/s). 1 RU ≈ el costo de leer un elemento de 1 KB. Cada operación (lectura, escritura, consulta, eliminación) consume RU: una sola métrica para rendimiento y costo.

DedicadoRU/s reservadas para un solo contenedor.
CompartidoRU/s a nivel de base de datos, compartidas por hasta 25 contenedores.

Las cuentas sin servidor se limitan a una sola región. Para distribución global, usar rendimiento aprovisionado.

Escalabilidad automática: se fija un máximo de RU/s y Cosmos DB ajusta la capacidad según la demanda real.

Para apps que necesitan esquema flexible, alcance global y baja latencia:

  • IoT y telemetría: ingesta rápida de datos de dispositivos, casi en tiempo real.
  • Juegos: perfiles, tablas de clasificación y estadísticas en milisegundos.
  • Comercio minorista: catálogos, carritos y pedidos a cualquier escala.
  • Apps web y móviles: personalización, funciones sociales e integraciones.
No es buena opción para combinaciones complejas de varias tablas (mejor Azure SQL Database) ni para análisis histórico a gran escala (mejor Microsoft Fabric o Azure Synapse Analytics).

Procesar datos = convertir datos crudos en información útil. Con dispositivos inteligentes e internet, mucha información puede procesarse en tiempo real como un flujo continuo.

Procesamiento por lotes

  • Se acumulan registros y se procesan juntos en una operación.
  • Se dispara por horario (cada hora), por cantidad de datos o por otro evento.

Analogía: estacionar los autos en un parqueo y contarlos todos en reposo. Ej. real: la factura mensual de la tarjeta de crédito.

VentajasDesventajas
Procesa grandes volúmenes de forma eficiente en un momento conveniente.Todos los datos deben estar listos antes de empezar.
Se programa en horas de poca carga (de noche).Retraso entre la entrada de datos y los resultados.
Un error pequeño (dato, bloqueo o programa) puede detener todo el lote; hay que validar antes de reejecutar.

Procesamiento de flujos (streaming)

  • Cada dato se procesa al llegar, sin esperar el siguiente lote.
  • Ideal cuando se generan datos nuevos de forma continua.

Analogía: contar los autos mientras pasan y sumar por intervalos (autos por minuto).

Ejemplos de streaming

  • Finanzas: sigue la bolsa en tiempo real, calcula el valor en riesgo y rebalancea carteras.
  • Juegos en línea: analiza las interacciones de los jugadores y ofrece incentivos al momento.
  • Inmobiliaria: recomienda propiedades según la ubicación del móvil del cliente.
  • Crítico en tiempo: un sistema de humo y temperatura activa alarmas y abre puertas ante un incendio.

3. Combinar lotes y flujos

  • Muchas soluciones usan ambos: datos históricos + tiempo real.
  • El streaming alimenta paneles en vivo (autos en la hora actual) y además guarda resultados en el almacén para el histórico (tráfico del último año).
  • Aunque no se necesite tiempo real, el streaming suele usarse para capturar datos y procesarlos después por lotes (desviar todos los autos al parqueo antes de contarlos).

4. Arquitectura lambda

Patrón común para combinar lotes y flujos:

1
Los eventos de streaming se capturan en tiempo real.
2
Los datos de otros orígenes se cargan a un almacén (normalmente un data lake) para procesamiento por lotes.
3
Si no se requiere tiempo real, los datos de streaming también se escriben al almacén para procesarlos por lotes.
4
Si se requiere tiempo real, una tecnología de flujos los prepara (filtra o suma por periodos) para análisis o visualización inmediata.
5
Los datos por lotes se procesan periódicamente y se guardan en el data warehouse para el histórico.
6
Los resultados del streaming también pueden guardarse en el warehouse.
7
Las herramientas de análisis y visualización muestran datos históricos y en tiempo real.

Spark Structured Streaming

Spark reparte el trabajo en un clúster de máquinas en paralelo; está en Fabric y Databricks y admite Python, Scala o Java para lotes y flujos. Structured Streaming trata el flujo como una tabla que crece:

  1. Se conecta a un origen (Event Hubs, carpeta, red).
  2. Lee los datos a una trama de datos (dataframe) que se llena sola.
  3. Se consulta (eventos por minuto, media móvil).
  4. Escribe los resultados en un destino.

Buena opción si ya usas Spark y quieres sumar tiempo real.

Fabric Real-Time Intelligence

Cubre todo el flujo, de la llegada de datos a la acción automática, en la misma área de trabajo:

  • Real-Time hub: catálogo central de los datos de streaming de la organización para descubrirlos y compartirlos.
  • Eventstreams: ingerir, enrutar y transformar flujos.
  • Eventhouse: BD para eventos y series temporales, consultada con KQL (Kusto Query Language).
  • Paneles en tiempo real: visualización de datos en vivo, con lenguaje natural y Copilot.
  • Activator: dispara acciones y alertas cuando los datos cumplen condiciones.
  • IA que genera consultas KQL a partir de preguntas en lenguaje natural.

Flujo: elegir un flujo → explorar patrones, anomalías y previsiones → paneles → alertas con Activator.

Delta Lake

Por defecto un data lake es solo una colección de archivos; Delta Lake le da garantías de base de datos:

  • Confiabilidad: registra los cambios; las escrituras parciales o fallidas no dañan los datos.
  • Validación del esquema: rechaza registros que no cumplen la estructura.
  • Lotes y streaming unificados: la misma tabla Delta es receptor de streaming y origen de consultas por lotes.
Delta Lake + Spark Structured Streaming = un solo almacén coherente para ingesta en tiempo real y análisis histórico.

3. Modelado de datos

Los modelos analíticos (en Fabric y Power BI: modelos semánticos) estructuran tablas relacionadas para el análisis:

  • Medidas: valores numéricos que se analizan (ingresos, cantidad).
  • Dimensiones: entidades por las que se agregan (producto, cliente, tiempo).

Ej.: ingresos totales por cliente o artículos vendidos por producto y mes.

Tablas

  • Dimensión: una fila por entidad con clave única y atributos (nombre, categoría, ciudad). Casi todos los modelos tienen una dimensión Tiempo.
  • Hechos: una fila por evento con sus medidas (una venta con cantidad e ingreso).
  • Estrella: hechos + dimensiones. Copo de nieve: dimensiones con tablas de detalle (Producto → Categoría).

Motor VertiPaq

Al cargar datos en un modelo semántico, Power BI los guarda en un almacén de columnas en memoria (VertiPaq). Las agregaciones se calculan al consultar, lo que da informes rápidos.

Jerarquías de atributos

Permiten subir o bajar (drill-down / drill-up) entre niveles de una dimensión:

  • Producto: producto → categoría.
  • Cliente: cliente → ciudad.
  • Tiempo: día → mes → año.

Ej.: ver ventas por año y bajar al detalle mensual; VertiPaq calcula cada nivel al consultar.

Modelado en Power BI

  • El modelo semántico se arma con tablas importadas de uno o varios orígenes.
  • En la vista Modelo de Power BI Desktop se crean relaciones entre hechos y dimensiones, se definen jerarquías, tipos de datos, formatos y otras propiedades.
  • Si los datos están en OneLake, usar Direct Lake: rendimiento en memoria sin paso de importación.

Trampas típicas: conceptos que se confunden

Evaluación de práctica gratuita en Microsoft Learn

Tipos de datos

  • Estructurados: tablas, CSV. Semiestructurados: JSON, XML. No estructurados: imágenes, video, PDF.
  • Trampa: JSON no es "no estructurado".

Formatos de archivo

  • Avro: por filas; encabezado JSON y datos binarios. Bueno para escribir y para streaming.
  • Parquet y ORC: por columnas; compresión y lecturas analíticas rápidas.

OLTP vs OLAP

  • OLTP: muchas transacciones pequeñas, datos normalizados, ACID.
  • OLAP: lecturas masivas de históricos, datos desnormalizados (esquema de estrella).
  • ACID: Atomicidad (todo o nada), Coherencia (de un estado válido a otro), Aislamiento (las transacciones no se interfieren), Durabilidad (lo confirmado persiste).

Roles

  • DBA disponibilidad, rendimiento, copias de seguridad, permisos.
  • ING canalizaciones: ingesta, limpieza, transformación.
  • ANA modelos, informes y visualizaciones.
  • Trampa: "crear un panel" es del analista, no del ingeniero.

SQL

  • DDL estructura: CREATE, ALTER, DROP, RENAME.
  • DCL permisos: GRANT, DENY, REVOKE.
  • DML datos: SELECT, INSERT, UPDATE, DELETE.
  • Trampa: DROP elimina la tabla (DDL); DELETE elimina filas (DML). DELETE sin WHERE borra todas las filas.

Normalización y objetos

  • Normalizar: una entidad por tabla, sin duplicados, relacionadas por PK/FK. Para análisis se desnormaliza.
  • Vista: consulta guardada que se usa como tabla virtual. Procedimiento almacenado: SQL reutilizable con parámetros. Índice: acelera lecturas, pero hace más lentas las escrituras.

Familia Azure SQL

  • IaaS SQL Server en VM: tú administras SO, parches y copias.
  • PaaS Managed Instance: instancia completa, compatibilidad casi total.
  • PaaS SQL Database: una BD o un grupo elástico; menos funciones de instancia.

Niveles de acceso de Blob

  • Frecuente uso constante. Esporádico ≥ 30 días. Poco frecuente ≥ 90 días. Archivo ≥ 180 días.
  • Trampa: Archivo está sin conexión; hay que rehidratar el blob (puede tardar horas) y solo se asigna por blob, no a la cuenta.
  • Menor costo de almacenamiento = mayor costo de acceso.

Redundancia

  • LRS: 3 copias en un centro de datos. ZRS: 3 zonas de la región.
  • GRS: LRS + copia en región secundaria. GZRS: ZRS + región secundaria.
  • Prefijo RA-: además permite leer de la región secundaria.

Storage: ¿cuál es cuál?

  • ADLS Gen2 no es un servicio aparte: es Blob Storage con espacio de nombres jerárquico habilitado.
  • Azure Files (SMB/NFS) ≠ Blob (acceso por HTTP/REST).
  • Table Storage: clave = PartitionKey + RowKey.

Cosmos DB

  • Coherencia, de más fuerte a más débil: Fuerte → Obsolescencia limitada → Sesión (predeterminada) → Prefijo coherente → Eventual.
  • Unidad de costo: RU; el rendimiento se aprovisiona en RU/s.
  • API nativa = NoSQL. Cassandra = familias de columnas; Gremlin = grafos.

Almacenes analíticos

  • Warehouse: relacional, esquema en escritura, SQL.
  • Data lake: archivos, esquema en lectura, Spark.
  • Lakehouse: lago + SQL gracias a Delta Lake (ACID sobre Parquet).
  • Hechos = valores numéricos; dimensiones = entidades para agrupar.

Lotes vs flujos

  • Lotes: todos los datos, latencia de horas, análisis complejo.
  • Flujos: datos recientes o ventanas, latencia de segundos, agregaciones simples.
  • Lambda: capa de lotes + capa de flujos. Kappa: solo flujos.

Power BI

  • Desktop crea; Servicio publica y comparte; Mobile consume.
  • Importación: copia los datos (VertiPaq), muy rápido, requiere actualizar. DirectQuery: consulta el origen en cada interacción. Direct Lake: lee tablas Delta de OneLake sin importar.
